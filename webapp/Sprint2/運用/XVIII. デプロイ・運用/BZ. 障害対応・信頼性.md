# BZ. 障害対応・信頼性

## 概要

信頼性工学（Site Reliability Engineering, SRE）は、システムの安定性を定量的に管理し、障害を予防・早期発見し、発生時に素早く対応するプラクティスです。

SLI/SLO の定義、監視・アラート設定、障害対応フロー、ポストモーテム実施、継続的な改善など、システムを「ユーザーに信頼される」レベルに保つための運用スキルを習得します。

---

## 1. SLI / SLO（信頼性指標）

**SLI（Service Level Indicator）:**

システムのパフォーマンスを定量的に測定する指標。

```
代表的な SLI:
- 可用性: リクエスト成功率 99.5%
- レイテンシ: P99 が 500ms 以下
- エラー率: 4xx / 5xx エラー 0.1% 以下
- データ完全性: ユーザーデータ欠損 0件
```

**SLO（Service Level Objective）:**

SLI に対する目標値。ビジネス要件と技術的実現可能性を両立させる。

```
例:

SLO: 「毎月、リクエスト成功率 99.9% を維持する」
  ↓ 計算
  = 月間 ダウンタイム許容値 = 30日 × 24h × 60min × (1 - 0.999)
  = 43.2分/月 ← 許容される停止時間

実際の可用性が SLO を下回る
  → エラーバジェット（回復余地）を消費
  → 0 になったら、新機能開発を止めて、信頼性向上に注力
```

**SLO ダッシュボード:**

```
リアルタイムダッシュボード:

API 可用性:
┌─────────────────────┐
│ 今月: 99.93%  ✓     │ ← SLO 達成
│ 27分 / 43分 消費    │
├─────────────────────┤
│ P99 レイテンシ:      │
│ 320ms  ✓             │ ← OK（目標 500ms）
├─────────────────────┤
│ エラー率:            │
│ 0.05%  ✓             │ ← OK（目標 0.1%）
└─────────────────────┘
```

## 2. 監視・アラート

**メトリクス収集:**

```
Prometheus / Datadog / CloudWatch で収集

- HTTP リクエストレート（req/sec）
- レスポンスタイム（P50, P95, P99）
- エラー率（4xx, 5xx）
- CPU 使用率（%）
- メモリ使用量（GB）
- ディスク I/O（iops）
- データベースクエリ実行時間
```

**アラート設定:**

```yaml
# Prometheus アラートルール例

- alert: HighErrorRate
  expr: |
    rate(http_requests_total{status=~"5.."}[5m])
    / rate(http_requests_total[5m]) > 0.05
  for: 5m
  annotations:
    summary: "エラー率が 5% を超過"
    description: "{{ $value }}% のリクエストがエラー（5m平均）"

- alert: HighLatency
  expr: |
    histogram_quantile(0.99, http_request_duration_seconds)
    > 1.0
  for: 10m
  annotations:
    summary: "P99 レイテンシが 1秒を超過"
    description: "{{ $value }}秒（目標: 500ms）"
```

**アラート疲れを防ぐ:**

```
❌ 悪い例：全ての異常をアラート
  → アラーム通知過多
  → エンジニアが無視する

✓ 良い例：実行可能な異常のみアラート
  - 実際に対応が必要な値
  - 継続期間で判定（一時的な揺らぎ除外）
```

## 3. 障害対応フロー

**インシデント検出から復旧まで:**

```
1. 検出（Detect）
   - 監視システムがアラート
   - または ユーザーから通報

2. 対応チーム招集
   - Slack #incidents で通知
   - 対応指揮官選出

3. 初期対応（Mitigation）
   - 原因の仮説立てる
     ├─ DB 接続プール枯渇？
     ├─ キャッシュ無効化？
     └─ 外部 API タイムアウト？
   - 応急処置で復旧
     ├─ 接続プール再起動
     ├─ 人工的にトラフィック制限
     └─ フェイルオーバー

4. 復旧確認
   - P99 レイテンシ正常化
   - エラー率が 0.1% 以下
   - ユーザー報告停止

5. ポストモーテム
   - 根本原因分析
   - 再発防止策の立案
```

**オンコール体制:**

24/7 体制で障害対応。

```
時間帯別に当番を配置:

時刻     │ 当番
─────────┼─────────
09-18    │ 勤務中の当番
18-22    │ 当番A（朝番）
22-06    │ 当番B（夜番）
06-09    │ 当番C（早朝番）

月 1 回のオンコール週間
基本給 + オンコール手当
```

**ハンドオーバーミーティング:**

当番交代時に、進行中の案件を引き継ぎ。

```
朝ミーティング:
前日夜番：「深夜 2時に API の一時的な遅延あり、
          原因特定中。何も対応不要」
朝番：「了解。進捗を追跡します」

引き継ぎ事項：
- 進行中の障害
- 監視中の異常
- デプロイ予定
```

## 4. 高信頼性アーキテクチャ

**冗長性（Redundancy）:**

単一障害点（SPOF: Single Point of Failure）を排除。

```
❌ 単一構成:
ユーザー → Load Balancer → サーバーA（単一）
              ↓
           RDS DB（単一）

問題: サーバーA が落ちたら、全ユーザーがサービス利用不可

✓ マルチAZ構成:
ユーザー → Load Balancer
             ├─ サーバーA（AZ-1）
             ├─ サーバーB（AZ-2）
             └─ サーバーC（AZ-3）
              ↓
           RDS マスター（AZ-1）
           RDS レプリカ（AZ-2）

効果: 1 つの AZ が停止しても、他が引き継ぎ
```

**自動フェイルオーバー:**

障害を検出し、自動的に健全なリソースに切り替え。

```
Health Check（5秒ごと）:
load-balancer → サーバーA: OK
             → サーバーB: OK
             → サーバーC: ❌ No Response

判定: サーバーC は不健全
動作: サーバーC を負荷分散から除外
結果: ユーザーは A/B に分散（ダウンタイムなし）
```

**クロスリージョンバックアップ:**

1 つのリージョン全体が障害を起こしても復旧。

```
プライマリ: 東京リージョン
バックアップ: 大阪リージョン

定期的に RDS スナップショット を大阪にコピー
障害時に、大阪からリストア
→ RPO（Recovery Point Objective）: 1時間以内
→ RTO（Recovery Time Objective）: 30分以内
```

**DNS フェイルオーバー:**

レコードを動的に変更。

```
Route53 ヘルスチェック:
example.com の A レコード
  ├─ 東京サーバー: 健全 ✓
  └─ 大阪サーバー: 健全 ✓

東京がダウン
Route53 が自動検出
A レコードを大阪に変更
→ DNS クライアントが大阪にアクセス
```

## 5. サーキットブレーカー

外部 API の障害が、自システム全体に波及するのを防止。

```javascript
const CircuitBreaker = require('opossum');

const breaker = new CircuitBreaker(
  async () => {
    return await externalAPI.request();
  },
  {
    timeout: 5000,              // 5秒でタイムアウト
    errorThresholdPercentage: 50, // エラー50%で開く
    resetTimeout: 30000,        // 30秒後に再試行
  }
);

breaker.on('open', () => {
  console.log('Circuit opened - falling back to cache');
  // フォールバック処理
  return cache.get('data');
});

app.get('/data', async (req, res) => {
  try {
    const data = await breaker.fire();
    res.json(data);
  } catch (err) {
    res.status(503).json({
      error: 'Service temporarily unavailable'
    });
  }
});
```

状態遷移:
```
Closed（正常）
  → エラー 50% 検出 → Open（遮断）
                        ↓（30秒後）
                      Half-Open（テスト）
                        ↓（成功）
Closed（正常に戻す）
```

## 6. ポストモーテム（無責任風土）

障害後に「何が起きたのか」を分析し、再発防止策を立案。

**目的:**
- 「誰が悪かったのか」を追求しない ← 非難文化を避ける
- 「システムの何が脆弱だったのか」を特定する
- 同じ障害を繰り返さない

```markdown
# ポストモーテム: 2024-02-01 API タイムアウト

## タイムライン

| 時刻 | イベント |
|------|--------|
| 14:23 | アラート: P99 レイテンシが 5秒 |
| 14:25 | 対応開始 |
| 14:27 | 外部 Weather API が遅い事を発見 |
| 14:30 | Weather API へのリクエストタイムアウト設定 |
| 14:33 | サービス復旧、ユーザーエラー停止 |

## 影響

- ダウンタイム: 10分
- 影響ユーザー: 約 5% （天気情報取得機能利用者）
- ビジネス影響: 売上損失 $500

## 根本原因

Weather API プロバイダーが サーバー過負荷状態
→ 応答時間が 30秒以上に悪化
→ アプリの API リクエストがタイムアウト待ち
→ リクエスト処理が ブロック状態になり、スレッドプール枯渇
→ 他ユーザーへの応答もできなくなる

## なぜ気づかなかったのか（5 Whys）

Q: なぜ Weather API の問題に気づかなかった？
A: タイムアウト設定がなかったため、無限に待つ

Q: なぜタイムアウト設定がなかった？
A: Weather API は「安定している」と信頼していた

Q: なぜそう信じた？
A: 実装時に障害シナリオを想定していなかった

Q: なぜシナリオテストをしなかった？
A: 「外部依存の障害対応」が要件に含まれていなかった

→ **根本原因: 要件定義が不完全**

## 改善策

| アクション | 担当 | 期限 |
|----------|------|------|
| Weather API に タイムアウト 3秒設定 | Backend | 2月2日 |
| フォールバック機構（キャッシュ利用） | Backend | 2月5日 |
| 外部 API 障害テスト を実施 | QA | 2月8日 |
| 外部 API 選定基準を文書化 | PM | 2月15日 |

## 学び

- 外部依存は必ず障害シナリオを想定する
- Chaos Engineering で弱点を事前発見する
- 監視をより詳細化する（API レスポンス時間別）
```

## 7. 避難訓練（Game Day）

本番環境で障害をシミュレートし、対応スキルを高める。

```
Game Day シナリオ:

【シナリオ】2024-02-15 15:00 実施

15:00 - セットアップ
  - Slack #game-day チャネル作成
  - ビデオ通話開始
  - 観察者（スコアリング担当）配置

15:05 - 障害注入（チャオスエンジニアリング）
  Pod A / B / C のうち、C を意図的に停止
  → 担当者には通知しない（本番相当）

15:05-15:25 - 対応フェーズ
  - 検出（アラート確認）
  - 原因特定（ログ/メトリクス確認）
  - 対応（トラフィック偏向など）
  - 復旧確認

15:25 - 振り返り
  - 良かった点（検出が早かった）
  - 改善点（ログがわかりづらかった）
  - アクションプラン策定

結果: 本番相当の対応スキルが磨かれる
```
