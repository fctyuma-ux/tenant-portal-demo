# コミュニケーション

## 概要

プロジェクト成功の鍵は、チーム内の効果的なコミュニケーションです。会議運営、ドキュメント作成、非同期コミュニケーション、障害報告など、様々なシーンでの実践的なコミュニケーションスキルを習得します。

良いコミュニケーションは、曖昧性を減らし、チーム全体の認識を揃え、問題を早期に発見するための基本となります。

---

## 1. 会議の進行・運営

**目的:** チーム全体で意思決定を行い、認識をすり合わせる

会議は、単に情報を共有するだけではなく、参加者が対等に意見を述べ、結論を導き出すプロセスです。

**アジェンダ作成の要素:**
- 開始時間・終了時間（タイムボックス）
- 各議題の目的（情報共有 or 意思決定 or ブレーンストーミング）
- 必須参加者の明示

**発散と収束:**
- **発散フェーズ:** 意見・アイデアを自由に出す、否定しない
- **収束フェーズ:** 意見を整理し、投票・多数決で決定する

**パーキングロット:** 会議の時間内に議論できない話題を記録し、後で検討対象にする。これにより脱線を防ぎ、時間を有効活用できます。

**会議進行の実践:**

```markdown
# 定例会議 - 2024年2月

## アジェンダ（60分）

1. 前週の進捗確認 （5分）
2. 今週の優先タスク決定 （30分） ← 意思決定
3. 技術検討：キャッシュ戦略 （20分） ← ブレーンストーミング
4. クローズ （5分）

## パーキングロット
- [ ] 長期的なリファクタリング計画（3月に検討）
```

## 2. ドキュメント・コミュニケーション

**README の鮮度管理:**

READMEは「最初に読む」ドキュメントです。古い情報があると、新しいメンバーは混乱します。

- **プロジェクト開始時:** ゼロから環境構築する手順を記載
- **定期的なテスト:** 実際に手順を最初から実行し、脱漏がないか確認
- **更新時:** 変更があれば即座に反映

**ドキュメント構成の3層:**

1. **ストック情報（検索可能）**
   - README / API仕様書 / セットアップガイド
   - 検索対象となるため、完全性が重要

2. **フロー情報（リアルタイム性）**
   - Slack / 日報（分報）/ チャット
   - 速報性が重要

3. **テンプレート・Tips**
   - よくある質問への答え
   - 「なぜこのやり方なのか」の解説

**再現性のある記述:**

```markdown
❌ 悪い例
「Node環境を作ってnpm installしてrun devする」

✓ 良い例
「Node.js 18以上を環境にインストール後、
npm install && npm run dev を実行。
http://localhost:3000 でアプリが起動します」
```

## 3. Diagram as Code / API仕様書

**シーケンス図の作成:**

システムの動作流れを図で示すことで、複雑な処理を視覚的に理解できます。

例: ユーザー認証フロー

```
User Browser      API Server      Database
 |                 |               |
 |--POST /login--->|               |
 |                 |---SELECT----->|
 |                 |<---User Data--|
 |                 |               |
 | Check Password  |
 |                 |               |
 |<--JWT Token-----|               |
 |                 |               |
```

**API仕様書（OpenAPI形式）:**

```yaml
paths:
  /users/{id}:
    get:
      summary: ユーザー情報取得
      parameters:
        - name: id
          in: path
          required: true
          schema:
            type: integer
      responses:
        '200':
          description: ユーザー情報
          content:
            application/json:
              schema:
                $ref: '#/components/schemas/User'
        '404':
          description: ユーザーが見つかりません
```

## 4. 非同期コミュニケーション

**同期 vs 非同期:**
- **同期（即座返答が必要）:** 緊急の障害報告、重要な判断
- **非同期（返答を急がない）:** 情報共有、進捗報告、質問

**No Hello ルール（効率的な質問）:**

❌ 悪い例：
```
10:00 田中：こんにちは
10:05 太郎：（返答を待つ）
10:10 田中：明日のミーティング時間変更できますか？
```

✓ 良い例：
```
10:00 田中：明日の定例会議を14:00に変更できますか？急いでいます
```

→ 相手は一度のメッセージで文脈を理解でき、すぐ返答できます

**分報（Times/Tweets）の活用:**

各メンバーが1日の進捗・学習内容を簡潔に投稿。チーム全体が暗黙的にお互いの動きを把握でき、質問しやすい関係が作られます。

## 5. インシデント管理・ポストモーテム

**インシデント管理フロー:**

```
1. 検出・通知 → 緊急対応チーム集合
   ├─ Slack #incidents で情報共有（リアルタイム）
   └─ 対応指揮官の選出

2. 初期対応 → 応急処置で復旧
   ├─ 原因推測（仮説）
   └─ 改善策の試行

3. 復旧確認 → 全機能が正常か検証

4. ポストモーテム → 根本原因の分析
   └─ 「犯人探し」ではなく「システムの改善」が目的
```

**Blameless Postmortem（無責任風土のポストモーテム）:**

障害の責任を追求するのではなく、「なぜそういう状況が起きたのか」をシステム全体で考えます。

```markdown
# ポストモーテム：2024-02-01 データベース停止

## 事象
本番環境のDBが10分間接続不可

## 影響
ユーザーは503エラーを経験、売上ロス: $5,000

## 根本原因
- ディスク容量が満杯 ← 監視アラートが無効だった
- 無効化した理由：誤検知が多かったため

## 改善
1. ディスク監視ロジックを改良（誤検知削減）
2. 自動削除スクリプトを導入
3. 定期レビュー会議を新設

## 誰が何をする
- [ ] インフラ担当：ディスク監視設定修正（2月7日まで）
- [ ] 運用担当：スクリプト導入テスト（2月10日まで）
```

**なぜなぜ分析（5 Whys）:**

深掘りして本当の原因を見つけます。

```
Q: なぜDBが停止した？
A: ディスク容量が満杯だった

Q: なぜ容量が満杯？
A: ログファイルが大きく増えていた

Q: なぜ増えた？
A: ログローテーション設定が間違っていた

Q: なぜ気づかなかった？
A: ディスク使用率アラートが無効だった

Q: なぜ無効？
A: 過去の誤検知が多かったため、手動で無効化した
→ ここが根本原因！
```

## 6. 技術文書・説明の質

**5W1H と PREP法:**

情報を構造的に整理します。

```markdown
## 機能: ユーザーマイページの実装

【5W1H】
- Who: 認証済みユーザー
- What: 自分の購入履歴・プロフィール を確認
- When: ログイン後、常時アクセス可能
- Where: /my-page ルート
- Why: ユーザーが自分の情報を管理したいため
- How: Next.js App Router + React Server Components

【PREP法】
1. Point（要点）: ユーザーマイページを実装
2. Reason（理由）: UX改善のため
3. Example（具体例）: 購入履歴表示、アドレス変更
4. Point（要点の再確認）: 実装期限は2月末
```

**手順書のユーザビリティテスト:**

ドキュメントを初心者に読んでもらい、「分かりにくい」部分を改善します。

```markdown
テスト対象: 「新規プロジェクトセットアップ手順」
実施者: インターン（初度実行）

課題:
- [ ] 「npm run build」でエラーが出た（手順が脱漏）
- [ ] コマンド実行順序が曖昧
- [ ] 環境変数の説明が不足

改善案:
1. 前提条件（Node 18以上）を明記
2. 各ステップに「期待される出力」を記載
3. よくあるエラーとその解決法を追加
```

## 7. 設計決定（ADR）の記録

**Architecture Decision Records（ADR）:**

「なぜこの技術/方針を選んだのか」を記録することで、将来的な見直し時に判断根拠がわかります。

```markdown
# ADR-005: キャッシュ戦略に Redis を選択

## ステータス
Accepted

## 文脈
- アクセス頻度の高いユーザープロフィール情報が、毎リクエスト DB から取得されている
- 現在、ページロード時間が 2秒 → 改善目標は 500ms

## 決定
Redis を キャッシュレイヤーとして導入

## 根拠
| 選択肢 | メモリ効率 | 応答速度 | 運用コスト | 選定 |
|-------|---------|--------|----------|------|
| Redis | ◎ | ◎ | ○ | ✓ |
| Memcached | ○ | ◎ | ◎ | 一考 |
| アプリメモリ | △ | ◎ | ◎ | スケール困難 |
| CDN | ○ | ◎ | △ | 静的資源向け |

理由:
- Redis: セッション管理も必要になる見込み
- Memcached: より複雑なデータ型が必要

## 結果
実装後、ページロード時間が 800ms に改善（目標未達だが約40%削減）
```
