# AO. 設計ドキュメント・意思決定

## 概要

設計ドキュメントは、アーキテクチャの決定と根拠を記録し、チーム全体での理解を統一するためのツールです。Docs as Code アプローチで、ドキュメントをコードと同じように管理・バージョニングすることで、鮮度を保ち、信頼性の高い設計情報を提供します。

---

## 1. 意思決定プロセス

複数の選択肢から、最適な実装方針を選定するプロセス。

**意思決定の質を高めるポイント:**
- 複数の選択肢を検討（最低3つ）
- 各選択肢の利点と課題を明記
- チーム全体でレビューと合意
- 決定の根拠を記録

**判定基準:**
- パフォーマンス：スケーラビリティ、応答時間
- 保守性：コードの読みやすさ、テストの容易さ
- コスト：開発期間、運用コスト
- 組織：チームのスキル、既存プラクティス

## 2. ADR（Architecture Decision Records）

重要な技術的決定を文書化するフォーマット。

**構成:**
```markdown
# ADR-001: データベース選択

## 状態
提案中 / 承認 / 実装中 / 完了 / 廃止

## コンテキスト
なぜこの決定が必要か

## 決定
何を選択したのか

## 根拠
選択の理由

## 結果
予想される影響
```

**例：**
```markdown
# ADR-001: マイクロサービス vs モノリシック

## 状態
承認

## コンテキスト
アプリケーションが成長し、デプロイの並列化が必要

## 決定
モノリシックアーキテクチャを継続

## 根拠
1. 現在のスケールではマイクロサービスの複雑性が不要
2. チームのマイクロサービス経験が限定的
3. 運用コストの増加が課題

## 結果
- 継続的な監視が必要
- 3年以内の再評価を計画
```

## 3. Docs as Code

ドキュメントをコードと同じように管理するアプローチ。

**メリット:**
- バージョン管理（Git）で履歴を追跡
- Pull Request でレビュー
- CI で自動ビルド・デプロイ
- Markdown で執筆可能

**ツール:**
- **静的サイト生成器：** MkDocs、Hugo、Docusaurus
- **バージョン管理：** Git（GitHub、GitLab）
- **ホスティング：** GitHub Pages、Netlify

**ワークフロー:**
```
Markdown で執筆
  ↓
PR 作成 → レビュー
  ↓
マージ（main）
  ↓
CI でビルド
  ↓
自動デプロイ（GitHub Pages）
```

## 4. エラーハンドリング設計

予期しない状況への対応方針を設計します。

**例外の翻訳（Exception Translation）:**
低レベルの例外を、アプリケーション固有の例外に変換。

```typescript
// DB エラー → アプリケーション例外に翻訳
try {
  const user = await db.findUser(id);
} catch (dbError) {
  // DB エラーを隠蔽し、アプリケーション例外を投げ
  throw new UserNotFoundError(`ユーザー ${id} が見つかりません`);
}
```

**エラーの握りつぶし回避:**
```typescript
// 非推奨：エラーを無視
try {
  const user = await db.findUser(id);
} catch (error) {
  // エラーを握りつぶす（何も出力しない）
}

// 推奨：ログ記録と再スロー
try {
  const user = await db.findUser(id);
} catch (error) {
  logger.error('ユーザー取得エラー', { id, error });
  throw error;
}
```

**エラーラッピング:**
コンテキスト情報を追加してエラーを拡張。

```typescript
try {
  const result = await externalAPI.call();
} catch (error) {
  throw new ApiError('外部API呼び出しエラー', {
    cause: error,
    endpoint: 'https://api.example.com/users',
    retryable: true,
  });
}
```

## 5. リトライ戦略

一時的な障害から復帰するメカニズム。

**Exponential Backoff（指数バックオフ）:**
```
リトライ回数: 1回目 - 待機時間: 1秒
リトライ回数: 2回目 - 待機時間: 2秒
リトライ回数: 3回目 - 待機時間: 4秒
リトライ回数: 4回目 - 待機時間: 8秒
```

**Jitter（ゆらぎ）の追加:**
複数のクライアントが同時にリトライするのを防ぐため、ランダムなディレイを追加。

```typescript
const delay = Math.pow(2, retries) * 1000 + Math.random() * 1000;
```

## 6. Circuit Breaker パターン

障害サービスへのアクセスを遮断し、自動復帰を試みるパターン。

**3つの状態:**
```
Closed（通常）→ リクエスト成功
   ↓ （失敗多発）
Open（開放）→ リクエストを即座に失敗
   ↓ （タイムアウト後）
Half-Open（半開）→ テストリクエストを1つ実行
   ↓ （成功）→ Closed に戻る
   ↓ （失敗）→ Open に戻る
```

## 7. エラーメッセージ設計

ユーザーが問題を理解し、対応できるメッセージ。

**要素:**
- **問題の説明：** 何が起きたのか
- **原因：** なぜ起きたのか（ユーザーが理解可能な範囲）
- **対応方法：** どうすべきか

**例：**
```
悪い例：
"エラーが発生しました"

良い例：
"メールアドレスの形式が不正です。
例：user@example.com の形式で入力してください。"
```

**セキュリティへの配慮:**
```
悪い例：
"ユーザー john@example.com は存在しません"
（ユーザー列挙攻撃に利用される）

良い例：
"ログイン情報が正しくありません。
メールアドレスとパスワードを再確認してください。"
```

## 8. エラーコード体系

エラーを分類・管理するためのコード体系。

```
エラーコード: [CATEGORY][SEVERITY][NUMBER]

例）
VALIDATION_ERROR_001   - 入力値エラー
AUTHENTICATION_ERROR_001 - 認証エラー
DATABASE_ERROR_001    - データベースエラー
RATE_LIMIT_ERROR_001  - レート制限エラー

HTTP ステータスコードとのマッピング：
VALIDATION_ERROR → 422 Unprocessable Entity
AUTHENTICATION_ERROR → 401 Unauthorized
DATABASE_ERROR → 500 Internal Server Error
```

## 9. 構造化ロギング

ログを機械可読形式で記録し、分析を容易にします。

```javascript
// 非構造化ログ
console.log('User login at 2024-01-15T10:30:00Z');

// 構造化ログ
logger.info('user.login', {
  userId: '12345',
  email: 'user@example.com',
  timestamp: '2024-01-15T10:30:00Z',
  ipAddress: '192.168.1.1',
  userAgent: 'Mozilla/5.0...',
});
```

**メリット：**
- ログ検索が容易（特定フィールドで フィルタリング）
- ダッシュボード化が可能
- アラート設定が容易

## 10. 設計ドキュメント の鮮度保持

ドキュメントを古いままにしない方法。

**実装方法：**
1. ドキュメントをコードのテストに組み込む
2. CI でドキュメントの同期性を検証
3. アーキテクチャ変更時は、ドキュメント更新を必須にする

**チェックリスト：**
- [ ] コード変更時、関連ドキュメントを更新した
- [ ] ドキュメント内の図（UML、ER 図）が現在の実装と一致する
- [ ] 例コードが動作確認済みである
- [ ] 定期的（四半期ごと）にドキュメントレビューを実施
