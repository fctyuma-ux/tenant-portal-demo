# AE. 企画・発見手法

## 概要

企画・発見手法は、ビジネス要件から実装可能な機能へと段階的に具体化するプロセスです。4つの階層で仮説を可視化し、優先順位を付けることで、チーム全体での認識相違を防ぎ、スコープクリープを回避します。

---

## 1. 4つの階層

**階層1：ビジネスゴール**
組織が達成したい最終目標。

```
例：オンラインストア
「顧客満足度の向上と売上増加」
```

**階層2：ユーザーニーズ**
ユーザーが達成したいこと。

```
例：
「より早く商品を探したい」
「信頼できるレビューを見たい」
```

**階層3：フィーチャー（機能）**
ユーザーニーズを満たすための具体的な機能。

```
例：
「高度な検索フィルター」
「レビュー投稿・表示機能」
```

**階層4：User Stories（ユーザーストーリー）**
実装単位の細粒度ストーリー。

```
例：
「ユーザーとして、価格範囲でフィルタリングしたい」
「ユーザーとして、星の数でレビューを絞り込みたい」
```

---

## 2. アサンプション（仮説）の可視化

仮説が正しいか、根拠なく決定していないかを可視化します。

**仮説マトリクス:**
```
         確実性が高い
            ↑
            |
[検証済み]  |  [仮説]
            |
            |
─────────────+────────→ 重要度が高い
            |
        [後回し]|
```

**例：オンラインストア**
```
検証済み（確実、重要）：
- ユーザーは検索機能を利用している ✓

仮説（未検証、重要）：
- ユーザーがレビュー機能を望んでいる（要検証）
- SNS シェア機能で売上が増加する（要検証）

後回し（未検証、低重要）：
- ユーザーがカスタマイズ可能なダッシュボードを望んでいる
```

**検証方法:**
- ユーザーインタビュー
- A/B テスト
- プロトタイプでのユーザーテスト

## 3. マップの作成

複数の観点から機能と優先度をマッピング。

**価値 vs 実装コスト のマトリクス:**
```
        実装コスト (低) ← → (高)

価値   [すぐ実装]    |    [後で検討]
(高)   └──検索機能────┘
      ┌──フィルター──┐
      │              │
      │ [中期計画]   │ [見送り検討]
      │              │
価値  └──カスタマイズ┘
(低)   └─ダッシュボード─┘
```

**重要度 vs 緊急度 のマトリクス（Eisenhower Matrix）:**
```
       緊急（今すぐ）| 非緊急（いずれ）
重要    └─バグ修正──┘  └─新機能開発──┘
（今後）
非重要  └─定常業務──┘  └──見送り───┘
```

## 4. 優先順位付け

複数の基準で機能に点数をつけ、優先度を決定します。

**スコアリング例：**
```
フィーチャー：「レビュー機能」

スコア基準：
├─ ユーザー価値（1-5）: 4点 → ユーザーが強く望んでいる
├─ ビジネス価値（1-5）: 3点 → 売上増加が限定的
├─ 実装複雑度（1-5）: 2点 → 比較的簡単
├─ リスク（1-5）: 1点 → 低リスク
└─ 合計スコア: (4+3-2-1) = 4

スコアが高いほど、優先度が高い
```

**決定ツール:**
- MoSCoW 法（Must / Should / Could / Won't）
- RICE スコアリング（Reach / Impact / Confidence / Effort）

## 5. バックボーン と スケルトン

製品構造を段階的に作成する手法。

**バックボーン（骨組み）:**
製品の基本構造。最も重要な機能や情報の流れ。

```
例：オンラインストア
├─ ホーム（入口）
├─ 商品検索・閲覧（中核機能）
├─ カート機能（重要）
└─ 決済（重要）
```

**スケルトン（骨格）:**
バックボーンに細部を加えたもの。ページ数、画面遷移を具体化。

```
ホーム
├─ ナビゲーション
├─ 検索バー
├─ 注目商品（カルーセル）
└─ フッター

商品一覧
├─ フィルター
├─ 商品グリッド
├─ ページネーション
└─ フッター

商品詳細
├─ 商品画像
├─ 説明・レビュー
├─ 「カートに追加」ボタン
└─ 関連商品
```

## 6. スライス（切り出し）

大きな機能を小さく分割し、段階的にリリース。

**機能を「スライス」で分割:**
```
大機能：「レビュー機能」

スライス1：「レビュー表示」
- ユーザーが既存レビューを読む
- リリース時期：第1期

スライス2：「レビュー投稿」
- ユーザーがレビューを投稿
- リリース時期：第2期

スライス3：「レビュー管理」
- ユーザーが自分のレビューを編集・削除
- リリース時期：第3期
```

**スライシングのメリット:**
- 早期フィードバック取得
- リスク軽減
- チーム の進捗可視化

## 7. ワークショップ の実施

ステークホルダー全体で、要件と優先度を合意するプロセス。

**参加者:**
- プロダクトマネージャー
- デザイナー
- エンジニア
- ビジネス部門

**アジェンダ例（2時間）:**
```
00:00-00:05：目的・ゴール確認
00:05-00:30：現状ユーザーニーズの共有（インタビュー結果等）
00:30-01:00：機能リストの脳内ダンプ（ブレストなし、列挙のみ）
01:00-01:30：グルーピング・カテゴリ化
01:30-01:55：優先順位付け（投票制）
01:55-02:00：まとめ・アクション確認
```

**成果物:**
- 機能リスト（優先順序付き）
- User Stories（大枠）
- リリース計画（スライス分割）

## 8. ウォーキングスケルトン

最小限の実装で、全体的な機能を体験できるプロトタイプ。

**特徴:**
- 全機能を浅く実装
- UI はモックアップレベル
- 重要な画面遷移は実装

**例：オンラインストア**
```
1. ホーム画面表示（静的）
2. 検索機能（モック検索結果）
3. 商品詳細表示（固定データ）
4. カート追加（ページ遷移のみ、実際には保存しない）
5. 決済画面表示（支払いボタンなし）
```

**利用目的:**
- チーム全体で「完成形」をイメージ共有
- ユーザーに見せて、大きな誤解がないか確認
- 段階的な開発計画の根拠を作成

**実装期間:**
通常、1-2週間で完成（詳細な実装は不要）

---

## 9. フィードバック収集

企画段階でのユーザー検証。

**検証タイミング:**
- バックボーン作成後
- ウォーキングスケルトン完成後

**検証方法:**
- ユーザーインタビュー（5-8名）
- クイックテスト（1時間）
- Figma プロトタイプ提示

**確認項目:**
```
□ 機能の必要性は確認できたか
□ 優先順位は正しいか
□ 大きな誤解がないか
□ ユーザーの想定外ニーズがないか
```

---

## 10. ドキュメント 化

企画フェーズでの決定を記録。

**必須ドキュメント:**
- Requirement Document（要件書）
  └─ ビジネスゴール、ユーザーニーズ、優先度
- Product Roadmap（ロードマップ）
  └─ リリース予定、スライス計画
- User Stories（ユーザーストーリー）
  └─ 詳細な受け入れ基準、タスク分割

**更新頻度:**
- 月1回の企画レビュー
- プロダクト成長に応じた見直し
