# H. デザインパターン

## 概要

デザインパターンは、再利用可能な問題解決策の設計テンプレートです。生成パターン（オブジェクト生成）、構造パターン（オブジェクト組み合わせ）、振る舞いパターン（オブジェクト間の責務分配）の3種類に分類されます。

AI生成コードのレビューにおいて、パターンの適切な活用とアンチパターン（設計の落とし穴）を識別できることが重要です。

---

## 1. 生成パターン（Creational Patterns）

**目的:** newの散在を抑え、オブジェクト生成の柔軟性と拡張性を確保

**主要なパターン:**

- **Factory（工場メソッド）:** 生成の窓口を一つに集約し、生成分岐を管理
- **Builder（ビルダー）:** 複雑な初期化パラメータを段階的に設定し、可読性を向上
- **Prototype（プロトタイプ）:** 既存オブジェクトを複製して差分を設定
- **Singleton（シングルトン）:** 単一インスタンスの確保（ただしテスト困難になる可能性）

**DI（Dependency Injection）による代替:**

Singletonパターンはテストをしにくくするため、コンストラクタ注入やファクトリメソッド + DIコンテナで代替が推奨されます。

---

## 2. 構造パターン（Structural Patterns）

**目的:** クラス・オブジェクトを組み合わせ、新しい機能を動的に追加

**主要なパターン:**

- **Adapter（アダプター）:** 互換性の異なるインターフェースを橋渡しし、ライブラリの差し替えを容易化
- **Decorator（デコレーター）:** 既存オブジェクトに機能を動的に追加（ログ、計測、キャッシング）
- **Facade（ファサード）:** 複雑なサブシステムを単一インターフェースで単純化
- **Proxy（プロキシ）:** オブジェクトへのアクセスを制御（遅延初期化、アクセス管理）
- **Composite（コンポジット）:** 木構造を再帰的に同一視し、統一的に扱う

**活用例:**
```typescript
// Decoratorで横断関心を追加
const cachedService = new CachedDecorator(
  new LoggingDecorator(baseService)
);
```

---

## 3. 振る舞いパターン（Behavioral Patterns）

**目的:** オブジェクト間の責務分配と相互作用を明確化

**主要なパターン:**

- **Strategy（戦略）:** 条件分岐を削減し、戦略を差し替え可能に
- **Observer（オブザーバー）:** イベント駆動で通知を購読・発行
- **Command（コマンド）:** 操作をオブジェクト化し、キューイング・undo/redoを実装
- **Iterator（イテレーター）:** 走査方法を統一し、内部構造に依存しない
- **State（ステート）:** 状態による振る舞い切替を整理

**状態遷移の実装例:**
```typescript
class OrderState {
  status: 'pending' | 'paid' | 'shipped';
  canCancel() { return this.status === 'pending'; }
}
```

---

## 4. アンチパターン（Anti-patterns）

**設計の落とし穴と改善方法:**

**God Object（神クラス）:** 責務が集中したクラス → 改善: SRPに従い責務を細分化

**Spaghetti Code（スパゲッティコード）:** 制御フローが複雑に絡み合う → 改善: Strategy, State, Commandで整理

**Copy-Paste Programming（コピペプログラミング）:** 重複コードの拡散 → 改善: 抽象化で統一

**Premature Optimization（時期尚早な最適化）:** 根拠のない最適化 → 改善: パフォーマンス測定後に実施

**Shotgun Surgery（散弾銃手術）:** 小さな変更が複数箇所に波及 → 改善: 凝集度を高め影響範囲を局所化

---

## 5. アーキテクチャレベルのパターン

**責務の層分け:**

- **MVC:** ビジネスロジック・表現・制御を分離
- **MVVM:** バインディングでViewとロジックを疎結合化
- **Repository:** 永続化を抽象化し、RDB/ファイル/APIの差し替えを容易化
- **Service Layer:** ユースケース・ビジネスルールを集約

**アンチ例:**

- **Fat Controller:** コントローラーにビジネスロジックが混在
- **Fat Model:** Modelが永続化と業務ロジック両方を担当

---

## 6. パターン認識とレビュー

**AI生成コードのレビュー観点:**

1. **パターンの正当性:** 選択されたパターンは問題を解決しているか？
2. **過度な抽象化:** 実装が複雑すぎないか？
3. **テスタビリティ:** 依存関係が複雑化していないか？
4. **一貫性:** コード全体でパターンの使用が統一されているか？

改善提案の手順: アンチパターン検出 → より適切なパターン提案 → 段階的なリファクタリング計画作成

---

## 7. 実装のポイント

- パターンはあくまで手段。問題がなければ使用しない
- 新人が理解できないほど複雑なら、Simpler Designを選択
- テスト困難なパターン（Singleton）は避け、DI推奨
- AI生成でもレビューフローで品質確保
