# X. その他の開発手法

## 概要

実装に至るまでのアプローチは TDD・BDD・DDD だけではありません。受け入れ基準から始まる ATDD（Acceptance Test-Driven Development）、ムダを排除する Lean 思想、組織的な Kanban・Scrum、UI パターン化の Storybook など、複数の手法を組み合わせることで、最適な開発フロー構築が可能です。

---

## 1. ATDD（受け入れテスト駆動開発）と受け入れ基準

ATDD は「受け入れ基準（Acceptance Criteria）」から始まる開発手法です。ビジネス要件を検証可能な基準として定義し、それを満たす開発を進めます。

**受け入れ基準の定義：**
- **何が「完成」か？** を明確化
- PO・QA・開発者の認識を統一
- テストと開発の指針となる

**受け入れ基準の例：**
```
機能：ユーザーログイン

受け入れ基準：
- Given: ユーザーはログインページを表示
- When: 有効なメール・パスワードを入力
- Then: ホームページにリダイレクトされ、ウェルカムメッセージが表示される

受け入れ基準：
- Given: ユーザーはログインページを表示
- When: 無効なパスワードを入力
- Then: エラーメッセージが表示され、ログインされない
```

**受け入れ基準の品質：**
- **検証可能：** テストで確認できるか？
- **明確：** 曖昧さがないか？
- **完全：** すべての happy path・エラーケースを網羅しているか？

---

## 2. スコープの切り方

大きな機能も小さな受け入れ基準に分割することで、段階的な開発が可能になります。

**悪いスコープ分割：**
```
Task: ユーザー管理機能を実装
受け入れ基準：
- ユーザーが登録・ログイン・プロフィール更新・削除できる
```
問題：大きすぎて、開発期間が長く、テストが複雑になる。

**良いスコープ分割：**
```
Task 1: ユーザー登録
受け入れ基準：
- メール・パスワードで登録
- 確認メール送信
- メール確認後にアカウント有効化

Task 2: ユーザーログイン
受け入れ基準：
- メール・パスワードでログイン
- セッション生成

Task 3: プロフィール更新
受け入れ基準：
- ユーザーは自分のプロフィールのみ更新可能
- 更新内容が保存される
```

**分割の指標：**
- 1 Task = 1～2 日の開発量
- 独立してテスト可能
- ビジネス価値が明確

---

## 3. 受け入れ基準から実装へ

受け入れ基準をテストに翻訳し、実装を進めます。

**フロー：**
1. **受け入れ基準定義：** PO・QA・開発で合意
2. **テスト作成：** 受け入れ基準から Unit/Integration テストを作成
3. **実装：** テストを pass させる実装
4. **QA 検証：** ユーザー観点で実装を検証
5. **リリース：** すべての受け入れ基準が満たされたことを確認

---

## 4. Lean 思想

ムダを排除し、価値を最大化する開発哲学です。

**ムダの7種類：**
1. **過剰な機能開発：** 使われない機能に時間をかける
2. **待機：** CI 完了待ち、レビュー待ち
3. **不要な処理：** 手作業で自動化できる処理
4. **欠陥：** バグ修正に時間がかかる
5. **情報伝達：** チーム間の認識ズレ
6. **複雑な実装：** 保守性が低いコード
7. **リソース未活用：** スキルが活かされない

**ムダを見つけるアプローチ：**
- リリースまでのリードタイムを測定
- 各段階でのボトルネックを特定
- 定期的に振り返り、改善案を実行

## 5. WIP制限と Flow

Kanban では「進行中（WIP: Work In Progress）」を制限し、スムーズなフローを実現します。

**WIP制限の効果：**
- コンテキストスイッチを削減（生産性向上）
- 完了までの時間短縮
- ボトルネックが可視化される

**例：Kanban ボード**
```
To Do          Doing (WIP: 3)    Review    Done
┌────────┐     ┌────────┐        ┌────────┐
│ Task A │  →  │ Task D │   →    │ Task G │
│ Task B │  →  │ Task E │   →    │
│ Task C │  →  │ Task F │
└────────┘     └────────┘        └────────┘
                 ↑
          WIP超過→タスク追加禁止
          完了待ちのタスクを優先化
```

**Flow メトリクス：**
- **リードタイム：** タスク開始から完了まで
- **サイクルタイム：** 開発開始から QA 完了まで
- **スループット：** 単位時間あたりの完了タスク数

---

## 6. 早いデリバリーとフィードバック

大きくリリースするより、小さく頻繁にリリースすることで、市場フィードバックを早期に得られます。

**小さくリリースするメリット：**
- リスク低減（問題が小さく、ロールバック容易）
- ユーザーフィードバック早期取得
- チーム間の認識統一が容易
- デプロイ自動化が容易

**リリースサイズの指標：**
- 1 リリース = 1 ユーザーストーリー か小機能
- テストカバレッジ 80% 以上
- リリース準備時間 < 1 時間

## 7. UI コンポーネント管理（Storybook）

UI の一貫性と再利用性を高めるため、コンポーネントを体系化して管理します。

**Storybook の役割：**
1. **UI カタログ：** すべてのコンポーネントを一覧表示
2. **ドキュメント：** 使用方法・Props を自動生成
3. **テスト基盤：** Visual Regression Test・E2E Test の対象
4. **デザイン・開発の協働：** デザインシステムの実装

**Storybook での状態管理：**
```typescript
// Button.stories.tsx
export default {
  title: 'Components/Button',
  component: Button,
};

export const Primary = {
  args: {
    label: 'Click me',
    variant: 'primary',
  },
};

export const Secondary = {
  args: {
    label: 'Click me',
    variant: 'secondary',
  },
};

export const Disabled = {
  args: {
    label: 'Disabled',
    disabled: true,
  },
};
```

## 8. コンポーネント境界の設計

責務が明確で、再利用しやすいコンポーネント設計が重要です。

**コンポーネント設計の原則：**
- **責務が明確：** 1 コンポーネント = 1 責務（Button は表示のみ）
- **Props は最小限：** 関心事ごとに Props を分離
- **バリエーション網羅：** すべての状態を Storybook で表現

**悪い設計：**
```typescript
// 責務が多すぎる
<UserForm
  onSubmit={handleSubmit}
  validation={schema}
  api={apiClient}
  router={router}
  theme={darkMode}
/>
```

**良い設計：**
```typescript
// 責務を分離
<Form onSubmit={handleSubmit} validation={schema}>
  <TextField label="Email" />
  <PasswordField label="Password" />
  <Button type="submit">Login</Button>
</Form>
```

## 9. UI の回帰検出

Visual Regression Test で、意図しない見た目の変化を自動検出します。

**ツール：**
- **Percy：** Cloud ベースの Visual Test
- **Chromatic：** Storybook 統合の Visual Test
- **Playwright：** スクリーンショット比較（self-hosted）

**実装例（Playwright）：**
```typescript
test('Button component renders correctly', async ({ page }) => {
  await page.goto('http://localhost:6006/?path=/story/components-button--primary');
  await expect(page).toHaveScreenshot('button-primary.png');
});
```

## 10. 実装観点

受け入れ基準から実装に至るまでのステップを明確化します。

**ATDD サイクル：**
```
1. 受け入れ基準作成
        ↓
2. テスト自動化（失敗状態）
        ↓
3. 最小限の実装（テスト成功）
        ↓
4. QA 手動確認
        ↓
5. リファクタリング（テスト green）
        ↓
6. リリース
```

**テスト観点の抽出：**
受け入れ基準：「ユーザーは有効なメール・パスワードでログインできる」
→ テスト観点：
- メール形式のバリデーション
- パスワード長の最小値
- DB からの正しいユーザー取得
- セッション生成
- 予期しない例外の処理

## 11. 組織的な Kanban / Scrum

Lean 思想に基づいたタスク管理フレームワーク。

**Kanban：** 継続的なフロー
- WIP 制限でボトルネックを特定
- ステップごとのメトリクス測定
- 継続的な改善サイクル

**Scrum：** 短いスプリント単位
- 1～4 週間のスプリント
- 定期的なレビュー・振り返り
- 予測可能なペースの維持

**組織によって選択：**
- 要件が明確 → Scrum
- 優先度が頻繁に変わる → Kanban
- 両方を組み合わせ → Scrumban

---

## 実施のポイント

- 受け入れ基準は「完成」を定義する。PO と開発で合意必須
- ムダを見つけるため、定期的にリードタイムを測定
- WIP 制限で流れを最適化
- UI コンポーネントは Storybook で管理・共有
- 小さくリリースしてフィードバック取得
