# V. 振る舞い駆動開発（BDD）

## 概要

振る舞い駆動開発（BDD: Behavior-Driven Development）は、ビジネス要件を実行可能なテストコードに落とし込む開発手法です。Gherkin 構文を用いることで、技術者とビジネス側が共通の言語で仕様を記述・検証できます。

---

## 1. Gherkin の構文

**基本構造：**

```gherkin
Feature: ユーザーログイン機能
  ユーザーが安全にログインでき、
  不正なアクセスを防ぐ

  Scenario: 正しい認証情報でログイン
    Given ユーザーが登録されている
    When ユーザーが正しいメールアドレスとパスワードを入力
    Then ログインが成功し、ホームページにリダイレクトされる

  Scenario: パスワードが間違っている
    Given ユーザーが登録されている
    When ユーザーが正しくないパスワードを入力
    Then エラーメッセージが表示される
    And ログイン画面に留まる
```

**各要素：**

- **Feature:** 大きな機能単位
- **Scenario:** 具体的なユースケース
- **Given:** 前提条件（初期状態）
- **When:** ユーザーが実行するアクション
- **Then:** 期待される結果
- **And / But:** 条件を追加

---

## 2. シナリオの粒度

**大きすぎるシナリオ（避ける）:**

```gherkin
# ✗ 複数のステップが混在
Scenario: 商品購入からレビュー投稿までの全フロー
  Given ユーザーがログイン
  When 商品を検索して
  And カートに追加して
  And 決済して
  And 商品を受け取って
  Then レビューを投稿する
```

**細かすぎるシナリオ（避ける）:**

```gherkin
# ✗ 1ステップだけ
Scenario: メールアドレスを入力
  Given ログイン画面が表示されている
  When メールアドレス入力欄に "test@example.com" を入力
  Then メールアドレスが入力欄に表示される
```

**適切な粒度（推奨）:**

```gherkin
# ✓ 1つのビジネス結果を検証
Scenario: 正しい認証情報でログイン
  Given ユーザーが登録されている
  When ユーザーがログイン画面でメールアドレスとパスワードを入力して送信
  Then ログインが成功し、ホームページにリダイレクトされる
```

## 3. 例外・境界条件の書き方

**ハッピーパス（正常系）:**

```gherkin
Scenario: 有効な商品数を注文
  Given 在庫に 10 個の商品がある
  When 5 個を注文
  Then 注文が確認され、在庫は 5 個に減少
```

**エラーケース（例外系）:**

```gherkin
Scenario: 在庫が足りない場合
  Given 在庫に 3 個の商品がある
  When 5 個を注文
  Then エラーメッセージが表示される
  And 在庫は変更されない

Scenario: 負の数を注文
  When -1 個を注文
  Then バリデーションエラーが表示される
```

**境界条件:**

```gherkin
Scenario: 在庫がちょうど 0 になる
  Given 在庫に 5 個ある
  When 5 個を注文
  Then 注文が確認され、在庫は 0 になる

Scenario: 最大注文数を超える
  When 1001 個を注文
  Then エラーメッセージが表示される
```

## 4. Gherkin で仕様をレビューして合意

**レビュープロセス:**

1. 開発者が Gherkin シナリオを記述
2. ビジネス側（PO）が読んで検証
3. 「このシナリオで正しい？」と確認
4. 合意後、実装開始

**メリット:**
- 誤解がない
- ビジネス要件が明確化される
- テストと仕様が一致

---

## 5. 仕様からテスト観点を抽出

**Gherkin から受け入れテストへの変換:**

```gherkin
Feature: パスワード変更機能
  Scenario: 正しい現在のパスワードで変更成功
    Given ユーザーがパスワード変更画面を開いている
    When 現在のパスワード、新しいパスワード、確認用パスワードを入力して送信
    Then パスワードが変更され、ログイン画面にリダイレクトされる
```

**テスト観点の抽出:**

- ✓ パスワードが DB で更新されているか？
- ✓ リダイレクトが発生しているか？
- ✓ 現在のパスワードが検証されているか？
- ✓ 新しいパスワードと確認用が一致しているか確認？
- ✓ 新しいパスワードは暗号化されているか？

**ユニットテスト / 統合テストで上記を検証**

## 6. BDD フレームワーク

**主要なツール:**

- **Cucumber:** Gherkin を実行可能なテストに変換（Ruby, Java, Python など対応）
- **Behave:** Python 向け
- **Cypress:** E2E テスト（JavaScript）
- **Playwright:** E2E テスト（複数言語対応）

**実装例（Cucumber with Jest）:**

```typescript
import { Given, When, Then } from '@cucumber/cucumber';

Given('ユーザーが登録されている', () => {
  // ユーザーを DB に作成
});

When('ユーザーがログインする', () => {
  // ログイン API を呼び出し
});

Then('ログインが成功する', () => {
  // ログイン結果を検証
  expect(response.status).toBe(200);
});
```

## 7. BDD のメリット

**ビジネスと開発の共通言語:**
- Gherkin は技術者・非技術者が読める
- 誤解が減る

**明確な受け入れ基準:**
- シナリオ = 受け入れ基準
- 合格条件が明確

**回帰テスト:**
- シナリオが実行可能テストになる
- CI で継続的に検証

---

## 8. BDD のデメリットと対策

**管理コスト:**
- Gherkin ファイル、テスト実装の二重管理
- 対策：自動化ツール、テンプレート化

**実装の複雑さ:**
- E2E テストは遅く、脆弱
- 対策：ピラミッド戦略（ユニット > 統合 > E2E）

---

## 9. テストピラミッド

```
        E2E (Scenario レベル)
      統合テスト
    ユニットテスト
```

**各層の役割:**

- **ユニットテスト（最下層）:** 関数・モジュールの単体テスト
- **統合テスト（中層）:**複数モジュール間の動作確認
- **E2E テスト（最上層）:** ユーザーシナリオの検証

**推奨配分:**
- ユニット：70%
- 統合：20%
- E2E：10%

---

## 10. 実装のポイント

- Gherkin で仕様を明確化し、ビジネス側と合意
- シナリオは適切な粒度で記述（大きすぎず、細かすぎず）
- 例外・境界条件を網羅
- テストピラミッド戦略で効率的にテスト
- CI で継続的に検証
