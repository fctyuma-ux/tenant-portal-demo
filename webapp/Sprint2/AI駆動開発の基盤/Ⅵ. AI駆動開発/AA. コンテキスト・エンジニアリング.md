# AA. コンテキスト・エンジニアリング

## 概要

コンテキスト・エンジニアリングは、AI モデル（特に大規模言語モデル）に適切な文脈情報を与え、高品質な出力を得るための実践的な手法です。仕様書の書き方、既存コードの提示、サンプルの提供などを通じて、AI の理解度を高め、要件に合致した実装を引き出します。

---

## 1. 仕様に含めるべき要素

AI に指示する際、曖昧さを最小化し、期待する動作を正確に伝える必要があります。

**必須要素：**

1. **入出力（I/O）の明確化**
   - 入力：データ形式、型、範囲（例：Email 文字列、正整数）
   - 出力：戻り値の型、形式、例

2. **例外・エラー処理**
   - 無効入力時の動作（throw vs return null）
   - エラーメッセージの形式

3. **制約・前提条件**
   - パフォーマンス要件（< 100ms）
   - セキュリティ要件（入力検証、暗号化）
   - 依存関係（使用禁止ライブラリ）

**仕様テンプレート：**
```markdown
## 関数：validateEmail

### 入力
- email: string（メールアドレス）

### 出力
- boolean（有効 = true、無効 = false）

### 例
- validateEmail("user@example.com") → true
- validateEmail("invalid.email") → false
- validateEmail("") → false

### 例外処理
- null または undefined が入力された場合 → false を返す
- 500文字を超える文字列 → false を返す

### 前提条件
- RFC 5322 準拠の検証を実施（簡易版で OK）
- 外部 API 呼び出し不可（正規表現のみで実装）
```

## 2. 既存コードの提示方法

AI に既存コードを見せることで、プロジェクトのパターン・スタイルを学習させます。

**提示のポイント：**
- **関連するコードのみ：** 全ファイルではなく、参考になる部分だけ
- **コンテキスト明記：** 「このファイルは User Entity の実装」など
- **パターンの説明：** 「このプロジェクトでは〇〇パターンを使用」

**例：**
```
既存の User Entity の実装を参考にしてください：

```typescript
// src/entities/User.ts
export class User {
  id: string;
  email: string;
  name: string;

  constructor(id: string, email: string, name: string) {
    this.id = id;
    this.email = email;
    this.name = name;
  }

  isActive(): boolean {
    // ビジネスロジック
  }
}
```

このプロジェクトでは、すべてのエンティティがコンストラクタで初期化され、ビジネスロジックはメソッドとして実装されています。Order Entity についても同じパターンで実装してください。
```

## 3. サンプル提示による期待形の明示

「こういう形で実装してほしい」という期待をサンプルコードで示します。

**サンプル駆動開発：**
```
以下のサンプルスタイルで実装してください：

"""typescript
class OrderService {
  constructor(private repository: OrderRepository) {}

  async createOrder(data: CreateOrderDto): Promise<Order> {
    // 入力検証
    this.validateInput(data);

    // ビジネスロジック
    const order = new Order(...);

    // 永続化
    await this.repository.save(order);

    // イベント発行
    this.eventBus.emit(new OrderCreated(order));

    return order;
  }
}
"""

このサンプルのように、以下を含めて実装してください：
1. 入力検証ステップ
2. ビジネスロジック
3. 永続化
4. イベント発行
```

## 4. 規約・ディレクトリ構成の伝達

AI が既存の規約に従うよう、明示的に伝えます。

**規約の明記：**
```
このプロジェクトの規約：

1. ファイル命名規則
   - エンティティ：Entity.ts（例：User.ts）
   - サービス：Service.ts（例：UserService.ts）
   - DTO：Dto.ts（例：CreateUserDto.ts）
   - テスト：*.test.ts（例：User.test.ts）

2. 関数命名規則
   - 非同期関数：async で始まる（例：async fetchUser()）
   - エンティティメソッド：動詞で始まる（例：isActive()）
   - ユーティリティ：get/set で始まる（例：getTotal()）

3. エラーハンドリング
   - カスタム例外を使用（ValidationError, NotFoundError 等）
   - エラーメッセージは日本語

4. ディレクトリ構成
```
src/
├── entities/        # ドメインモデル
├── services/        # ビジネスロジック
├── repositories/    # データアクセス
├── dto/            # データ転送オブジェクト
├── errors/         # カスタム例外
└── utils/          # ユーティリティ
```
```

## 5. 変更要求への対応

AI 生成コードを修正する際、「なぜ変更が必要か」を含めて指示します。

**修正指示の例：**
```
前回の生成コードを修正してください。

問題：
- getCurrentUser() が null 返却時のハンドリングがない
- パスワード検証が実装されていない

修正要件：
1. null チェックを追加し、NotFoundError をスロー
2. bcrypt を使用したパスワード検証を実装
3. 検証失敗時は InvalidCredentialsError をスロー

修正後のテストケース：
- getUser(validId) → User を返す
- getUser(invalidId) → NotFoundError をスロー
- authenticate(email, correctPassword) → true を返す
- authenticate(email, wrongPassword) → InvalidCredentialsError をスロー
```

## 6. 互換性とバージョニング

既存システムとの互換性を維持しながら、段階的に改善する指示方法。

**互換性維持の指示：**
```
旧 API との互換性を保ちながら、新しい形式を追加してください。

既存 API（変更不可）：
GET /api/users/:id
レスポンス：{ id, name, email, createdAt }

新 API（新規追加）：
GET /api/v2/users/:id
レスポンス：{ id, name, email, createdAt, updatedAt, status }

実装方針：
1. 既存エンドポイントは新しい形式で返却（互換性維持）
2. v2 エンドポイントは拡張フィールドを含む
3. テストで両方のエンドポイントが動作することを確認
```

## 7. AI 仕様テンプレートの作成

チーム内で再利用可能な仕様テンプレートを整備します。

**テンプレート例：**
```markdown
# [機能名] の仕様

## 概要
[何をする機能か]

## 入力
| 名前 | 型 | 説明 | 例 |
|------|-----|------|-----|
| email | string | メールアドレス | user@example.com |
| password | string | パスワード（8文字以上） | Pass1234 |

## 出力
| 名前 | 型 | 説明 |
|------|-----|------|
| token | string | JWT トークン |

| 条件 | 例外 | メッセージ |
|------|------|----------|

| パスワード不正 | InvalidPasswordError | パスワードが間違っています |

## テストケース
- ✓ 正常系：有効な認証情報でログイン
- ✓ メール未登録
- ✓ パスワード不正
- ✓ 入力なし（null/undefined）

## 実装上の制約
- TypeScript を使用
- bcrypt でパスワード暗号化
- エラーは日本語
- テストカバレッジ 80% 以上
```

## 8. AI 出力のレビュー観点

AI 生成コードを効率的にレビューするための確認項目。

**仕様合致性：**
- ✓ 入力値の検証が実装されているか？
- ✓ すべてのエラーケースが処理されているか？
- ✓ 出力形式が仕様に合致しているか？

**コード品質：**
- ✓ 既存の規約に従っているか？
- ✓ 読みやすいコードか？
- ✓ テストが含まれているか？

**セキュリティ：**
- ✓ SQL インジェクション対策はあるか？
- ✓ 入力サニタイゼーションはあるか？
- ✓ センシティブ情報ログ出力していないか？

## 9. 反復的なコンテキスト改善

最初の仕様が不完全な場合、AI の出力を見て仕様を改善します。

**フロー：**
1. 仕様 v1 を AI に提示
2. AI が実装を生成
3. 実装を確認し、足りない要件を特定
4. 仕様 v2 を AI に提示（修正指示）
5. AI が改善版を生成
6. 繰り返し

**改善例：**
```
初版仕様：「ユーザー作成関数を実装」
↓ AI 出力を確認
問題：エラーメッセージが英語

修正仕様：「ユーザー作成関数を実装。エラーメッセージは日本語で」
↓ AI 出力を確認
問題：作成日時が ISO 形式でない

修正仕様：「ユーザー作成関数を実装。エラーメッセージは日本語。createdAt は ISO 8601 形式」
↓ 満足
```
