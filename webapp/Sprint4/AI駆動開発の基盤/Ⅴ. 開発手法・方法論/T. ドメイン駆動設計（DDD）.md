# T. ドメイン駆動設計（DDD）

## 概要

ドメイン駆動設計における**ドメインイベント**は、ビジネス上の重要な事実をシステムに記録するメカニズムです。ビジネスルールが何かが起こったこと（購入が確定した、在庫が減った）を表現し、後続処理を駆動します。

---

## ドメインイベントとは（事実の記録）

**ドメインイベント**は、ビジネスドメインで発生した「重要な出来事」を表現するデータ構造です。

**特徴:**
- 過去時制で記述（〜が起きた）
- 一度発火すると変更不可（不変）
- イベント発火時点の関連情報をすべて含む

**例:**
- 「注文が確定した」 → OrderPlaced
- 「在庫が確保された」 → InventoryReserved
- 「支払いが処理された」 → PaymentProcessed

```typescript
// 不変なドメインイベント
class OrderPlaced {
  constructor(
    public orderId: string,
    public customerId: string,
    public totalAmount: number,
    public timestamp: Date
  ) {}
}
```

---

## イベント名と粒度（過不足）

**イベント名の命名:**
- ビジネス用語で、過去が完了形で記述
- 実装詳細を含めない
- 粒度は「最小の有意な単位」

**粒度の判断基準:**

粗粒度（悪い例）：
- 「OrderProcessed」→ 何が起きたのか不明確

細粒度（良い例）：
- 「OrderConfirmed」「PaymentCaptured」「InventoryDeducted」

各イベントが**1つの重要な事実**を表すように設計します。

---

## 整合性（同期処理と非同期処理の切り分け）

ドメインイベントから後続処理への応答は、**同期処理**と**非同期処理**に分けて考えます。

**同期処理が必要な場合:**
- イベント発火直後に状態が確定する必要がある
- 例）注文確定直後に在庫チェック（即座に在庫不足を返す）

**非同期処理が適切な場合:**
- 後続処理が独立した関心事
- 例）注文確定後のメール送信、ポイント加算

```typescript
// 同期: 購入時の在庫確保は即座に
async placeOrder(order) {
  const reserved = await inventory.reserve(order.items);
  if (!reserved) throw new InsufficientInventory();

  // イベント発火
  this.events.push(new OrderPlaced(order.id, ...));
}
```

---

## イベントストーミング/イベントモデリング

ステークホルダー全員で付箋を使い、ドメインイベントをブレインストーミング。プロセス入口から各ステップの出来事を整理し、分岐・並行処理を確認します。

---

## イベントを設計して後続処理を整理できる

1. 主要なビジネスイベントをリストアップ
2. イベントの前提条件と副作用を整理
3. 同期／非同期の切り分けを決定

---

## イベントの契約（スキーマ）を意識できる

イベントが複数部品に購読される場合、スキーマは**契約**として機能。JSON Schema で定義し、後方互換性を保持（新フィールドはoptional）。
