# AN. API設計

## 概要

API設計は、システム間の契約を定義する重要なフェーズです。このセクションでは、統合テストの種類、特定ケースの検証方法など、API の品質を担保するための手法を学びます。

---

## インテグレーションテストとの違い

テストには複数のレベルがあり、それぞれ異なる目的を持ちます。

**ユニットテスト**
- 単一の関数 / メソッドをテスト
- 依存関係はモックで代替
- 実行速度：高速（ミリ秒）

**インテグレーションテスト**
- 複数のコンポーネント/サービスを組み合わせてテスト
- 実際のDB、キャッシュなどを使用
- API呼び出しなど、外部との相互作用を検証
- 実行速度：中程度（秒単位）

**エンドツーエンドテスト（E2E）**
- ユーザーの実際の操作フロー全体をテスト
- UI から Backend まで、すべてのレイヤーを検証
- 実行速度：遅い（分単位）

**API統合テストの焦点:**
- API リクエスト / レスポンスの仕様に従うか
- エラーハンドリングが適切か
- 複数APIの呼び出し順序は正しいか
- 認証 / 認可が機能するか

---

## API設計時のチェックリスト

HTTPメソッド適切さ、パス/クエリ パラメータの設計、リクエスト/レスポンス スキーマ定義、認証方式、ページネーション、レスポンス時間目標。

---

## 特定ケースの検証

正常系、バリデーション失敗、認証なし、リソース未検出、大量データなどのエッジケースを検証。

---

## API仕様書の作成

OpenAPI / Swagger でエンドポイント、リクエスト/レスポンス、エラーパターン、認証方式を文書化します。

---

## ステータスコードの統一

- 200 OK / 201 Created：成功
- 400 Bad Request：入力エラー
- 401 Unauthorized：認証が必要
- 403 Forbidden：権限なし
- 404 Not Found：リソース未検出
- 500 / 503：サーバーエラー

---

## バージョニング戦略

後方互換性を保つため、URLパス（/v1/）またはヘッダーでバージョン管理。新フィールド追加は許可、既存フィールド削除は非推奨。
