# AY. リレーショナルデータベース

## 概要

リレーショナルデータベースのパフォーマンス最適化は、システム全体の応答速度に直結します。インデックス戦略、クエリ最適化、バックアップ・リカバリ戦略を理解することで、堅牢で高速なデータベースシステムを構築できます。

---

## インデックス戦略

**B-Treeインデックス** は、リレーショナルデータベースの標準的なインデックス構造です。ツリー構造により、ランダムアクセスと範囲検索の両方が効率的です。

- **単一カラムインデックス：** 一つのカラムのみ索引
- **複合インデックス：** 複数カラムを組み合わせたインデックス

**複合インデックス (Composite Index)** は、複数カラムに対するクエリを高速化します。

```sql
-- ユーザーを名前でソート後、作成日で絞り込む場合
CREATE INDEX idx_user_name_created ON users(name, created_at);

-- このインデックスが効果的：
SELECT * FROM users WHERE name = 'John' AND created_at > '2024-01-01';

-- このクエリではインデックスの一部のみ使用：
SELECT * FROM users WHERE created_at > '2024-01-01';
```

**インデックス設計のポイント:**
- WHERE句で頻繁に使用されるカラムを選定
- カーディナリティ（一意値の数）が高いカラムを優先
- 不要なインデックスは削除（ディスク容量・更新速度への悪影響）

## クエリ最適化と性能分析

**EXPLAINコマンド** は、クエリ実行計画を可視化します。

```sql
EXPLAIN ANALYZE SELECT * FROM users WHERE email = 'john@example.com';
```

出力から「Seq Scan」（全テーブルスキャン）が見られる場合、インデックス追加を検討します。

**N+1問題** は、1回のメインクエリに対して、結果レコード数分の追加クエリが発生する状況です。

```javascript
// ❌ N+1問題の例
const users = await db.query('SELECT * FROM users');
for (const user of users) {
  const posts = await db.query('SELECT * FROM posts WHERE user_id = ?', [user.id]);
  // N+1回のクエリが発生
}

// ✅ JOINで解決
const usersWithPosts = await db.query(
  'SELECT u.*, p.* FROM users u LEFT JOIN posts p ON u.id = p.user_id'
);
```

## バックアップ・リカバリ戦略

**バックアップ種類:**
- **フルバックアップ：** 全データをコピー（時間がかかるが復旧時間が短い）
- **差分バックアップ：** 前回バックアップ以降の変更分のみ
- **増分バックアップ：** 前回バックアップ以降の変更分のみ（より細かい粒度）

**PITR（Point-in-Time Recovery）** により、任意の時刻の状態にデータベースを復旧できます。ウォルアーカイブが必要です。

```
10:00 フルバックアップ
10:30 増分バックアップ
11:00 データ削除（致命的ミス）
  ↓
PITR で 10:50 の状態に復旧
```

## スロークエリの改善

**スロークエリの特定:**
- `slow_query_log` を有効化
- クエリ実行時間の閾値を設定（例：1秒以上）

```sql
SET GLOBAL slow_query_log = 'ON';
SET GLOBAL long_query_time = 1;
```

**改善パターン:**
1. インデックス追加
2. JOINの効率化
3. サブクエリの最適化
4. パーティショニング（大規模テーブル）

## ベストプラクティス

- **定期的なメンテナンス：** インデックスの再構築、テーブル統計の更新
- **リード・レプリカ：** 読み取り負荷分散
- **監視：** 接続数、キャッシュヒット率、スロークエリの監視
- **レプリケーション：** 高可用性のための同期レプリケーション
