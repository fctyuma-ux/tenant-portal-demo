# AX. サーバーレス・エッジ

## 概要

サーバーレスアーキテクチャは、インフラストラクチャ管理を不要にし、スケーラビリティと運用負荷の削減を実現します。このセクションでは、サーバーレスのメリット・デメリット、ステートレス性の原則、実装例を学習します。

---

## サーバーレスのメリット・デメリット

**メリット:**
- **スケーラビリティ：** 自動スケーリング、トラフィック変動への対応が容易
- **コスト削減：** 実行時間分のみ課金、アイドル時間のコスト不要
- **運用負荷削減：** インフラ管理、OSパッチ適用が不要
- **デプロイ簡易化：** コード変更のみでデプロイ完了

**デメリット:**
- **コールドスタート遅延：** 初回実行時に起動時間が必要（数秒）
- **デバッグの困難性：** ローカル環境での再現が難しい場合がある
- **ベンダーロックイン：** クラウドプロバイダに依存
- **ステートレス性の制約：** サーバー間の状態保持が困難

---

## ステートレス性

サーバーレス関数は、呼び出し毎に新しいインスタンスが生成されるため、メモリ内のデータは永続されません。すべての状態を外部ストレージ（データベース、キャッシュ）に保存する必要があります。

**実装の原則:**
- 関数内で状態を保持しない
- 外部ストレージに状態を委譲
- 環境変数で設定値を管理
- セッション管理はキャッシュシステムを利用

---

## Hello World関数のデプロイ

**AWS Lambdaでの最小実装:**
```javascript
export const handler = async (event) => {
  console.log('Event:', event);

  return {
    statusCode: 200,
    body: JSON.stringify({
      message: 'Hello from Lambda!',
      timestamp: new Date().toISOString(),
    }),
  };
};
```

**環境変数の利用:**
```javascript
export const handler = async (event) => {
  const apiKey = process.env.API_KEY;
  const environment = process.env.NODE_ENV || 'production';

  console.log(`Running in ${environment} mode`);

  return {
    statusCode: 200,
    body: JSON.stringify({ success: true }),
  };
};
```

環境変数は関数の設定画面またはIaC（Terraform、CloudFormation）で管理します。

## DB接続数枯渇問題

サーバーレス環境では、関数の並行実行数に応じてデータベース接続が増加します。デフォルトの接続プール設定では枯渇リスクが高まります。

**対策:**
- **接続プーリング：** RDS Proxy、PgBouncer を導入
- **接続数制限：** 関数ごとの接続数上限設定
- **コネクションの再利用：** Lambda内でコネクション再利用（グローバルスコープの活用）

---

## イベントソース

サーバーレス関数は、様々なイベントソースにより自動的にトリガーされます。

**一般的なイベントソース:**
- **API Gateway：** HTTP/RESTリクエスト
- **S3：** ファイルアップロード・削除
- **DynamoDB Streams：** データベース変更
- **CloudWatch Events：** スケジュール実行
- **SNS/SQS：** メッセージキュー

イベント駆動アーキテクチャを活用することで、マイクロサービス化が容易になります。

---

## ベストプラクティス

- **コールドスタート最小化：** バンドルサイズを削減、軽量な依存ライブラリを選定
- **エラーハンドリング：** 予測可能なエラーレスポンス定義
- **ログ設計：** CloudWatch Logsで構造化ログを記録
- **タイムアウト設定：** 最大実行時間を適切に設定（デフォルト3秒）
