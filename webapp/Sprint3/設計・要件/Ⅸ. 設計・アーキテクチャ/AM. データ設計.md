# AM. データ設計

## 概要

データ設計は、アプリケーションのドメインロジックを永続化層で正しく表現するプロセスです。ACID特性を保証しながら、パフォーマンスと保守性のバランスを取ることが重要です。データライフサイクル管理、トランザクション設計、マイグレーション戦略を含みます。

---

## 1. トランザクション管理

**ACID特性：** Atomicity（原子性）、Consistency（一貫性）、Isolation（独立性）、Durability（永続性）

トランザクション分離レベル（Isolation）には複数の段階があります：
- **Read Uncommitted:** 最も低い分離度、ダーティリードのリスク
- **Read Committed:** デフォルト設定が多い、実用的
- **Repeatable Read:** ファントムリードが発生可能
- **Serializable:** 最も厳格、パフォーマンスへの影響

**ロック戦略：** 楽観的ロック（バージョン番号）は競合が少ない場合に効率的です。悲観的ロック（行ロック）は競合が頻繁な場合に適しています。競合状態を防ぐには、適切なロック戦略とバリデーション実装が必須です。

---

## 2. データライフサイクル

**段階的な管理：** データ生成 → 活用 → 非活化 → アーカイブ → 削除

**削除戦略：** 論理削除（削除フラグの設定）は監査証跡を保持し、物理削除より復旧性に優れています。バックアップ・アーカイブは保持期間に応じて自動化します。退会ユーザーデータなど、規制要件によっては完全削除が必要な場合があります。

---

## 3. 時間の取り扱い

**有効期間（Valid Time）：** ビジネス上の有効期間（例：契約開始日～終了日）

**トランザクション時間：** システムがデータを管理した時間（更新日時）

**Slowly Changing Dimensions (SCD)：** 緩変化する次元データの履歴管理パターン。履歴テーブルパターンで実装し、変更履歴を自動記録します。

---

## 4. マイグレーション戦略

マイグレーションツール（Flyway、Liquidbase等）で段階的に適用し、破壊的変更（カラム削除等）への対処が必要です。**ダウンタイムなしの移行**では、新旧カラムを共存させる二重書き込みパターンを使用します。

**シーディング：** テストデータの自動投入は再現性と一貫性を確保します。

```sql
-- マイグレーション例（新カラム追加）
ALTER TABLE users ADD COLUMN email_verified_at TIMESTAMP;
UPDATE users SET email_verified_at = updated_at WHERE status = 'active';
```

---

## 5. データフロー設計

**DFD (Data Flow Diagram)：** データの入出力経路を可視化し、ボトルネックを特定します。

**ETL / ELT：**
- ETL（抽出→変換→ロード）：オンプレミス向け、変換後にロード
- ELT（抽出→ロード→変換）：クラウド向け、ロード後にDW内で変換

**データ系統（Data Lineage）：** どのソースからどのように変換されたか追跡可能にします。入出力仕様を定義し、データパイプラインを構築します。

---

## 6. トランザクションスコープ

**スコープの決定：** ロングトランザクションは避け、複数テーブルの一括更新では宣言的トランザクションを使用します。外部サービス呼び出しはトランザクション外で実行し、リトライロジックで対応します。

```python
# トランザクション分離：外部呼び出しを除外
with transaction.atomic():
    user = User.objects.select_for_update().get(id=user_id)
    user.balance -= amount
    user.save()

# 外部サービス呼び出しは別で
notify_user.delay(user_id)
```
