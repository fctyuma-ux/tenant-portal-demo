# AO. 設計ドキュメント・意思決定

## 概要

設計上の意思決定を記録・共有することで、チーム全体の判断根拠を明確にし、将来の類似判断を効率化します。ADR（Architecture Decision Record）は意思決定の形式化手法であり、品質特性のトレードオフを意識的に選択します。

---

## 1. 品質特性のトレードオフ

すべての設計判断は複数の品質特性の競合をはらんでいます。

**例：** キャッシュの導入
- **利点：** パフォーマンス向上（応答時間短縮）
- **欠点：** 一貫性低下（古いデータ表示の可能性）、複雑性増加（キャッシュ無効化ロジック）

**判断フロー：**
1. 候補案を列挙（キャッシュなし、Redis、CDN）
2. 各特性でスコアリング（パフォーマンス、保守性、コスト）
3. コンテキストに応じた優先順位付け
4. 選択理由を記録

---

## 2. ADR（Architecture Decision Record）

**形式：** MADR（Markdown ADR）が標準。簡潔で Git 管理可能。

**構成要素：**
1. **タイトル：** 決定内容を簡潔に
2. **状態：** Proposed → Accepted → Superseded
3. **コンテキスト：** なぜこの判断が必要か
4. **決定：** 選択した案
5. **結果：** ポジティブ・ネガティブな影響
6. **タイムスタンプ：** 記録日時

**テンプレート例：**

```markdown
# ADR-001: データベースエンジンの選定

## 状態
Accepted

## コンテキスト
スケーラブルなリレーショナルDB が必要。MySQL vs PostgreSQL の検討。

## 決定
PostgreSQL を採用。JSON型、UUID、ウィンドウ関数の豊富さが理由。

## 結果
- ポジティブ：高度なクエリ、コミュニティ充実
- ネガティブ：学習曲線、ホスティングコスト増加
```

---

## 3. リトライロジック設計

**外部APIの失敗対応：** ネットワークエラー・タイムアウトに対して自動リトライ。

**指数バックオフ：** リトライ間隔を段階的に増加させ、サーバー負荷を軽減。
- 1回目：2秒
- 2回目：4秒
- 3回目：8秒
- 最大試行回数：3～5回

```python
import time
def retry_with_backoff(func, max_attempts=3):
    for attempt in range(max_attempts):
        try:
            return func()
        except Exception as e:
            if attempt == max_attempts - 1:
                raise
            wait_time = 2 ** attempt
            time.sleep(wait_time)
```

**べき等性：** 同じリクエストを複数回実行しても副作用なしの設計が必須。

---

## 4. ADR の運用

**作成タイミング：** 重要な技術判断・アーキテクチャ変更があった際。些細なバグ修正は不要。

**レビュープロセス：**
1. 提案者が `docs/adr/` に新規 ADR を作成
2. チーム内で設計レビュー
3. 承認後、Accepted に変更
4. 古い ADR は Superseded に

**ドキュメント更新：** ADR 決定は README・アーキテクチャガイドに反映。

---

## 5. 設計ドキュメントの体系

**階層構造：**
- **L1：** アーキテクチャ概要図（全体像）
- **L2：** コンポーネント間のデータフロー
- **L3：** API 仕様・スキーマ定義
- **L4：** 実装パターン・コード例
