# AL. アーキテクチャパターン

## 概要

アーキテクチャパターンは、システムの信頼性・スケーラビリティ・保守性を実現するための設計の型です。通信パターン、マイクロサービス、技術的負債管理、段階的移行などを統合的に検討します。

---

## 1. 通信パターンの選択

**同期通信 vs 非同期通信:**
- **同期通信（リクエスト・レスポンス）:** ユーザーが結果をすぐに確認できる。サービス間の依存性が強い
- **非同期通信（メッセージキュー）:** サービス間の結合度が低い。スケーラビリティに優れるが、トランザクション管理が複雑

**Pub/Subモデル:**
- イベント駆動アーキテクチャの基本パターン
- 発行者（Publisher）と購読者（Subscriber）が疎結合
- 例：ユーザー登録完了イベント → メール送信、プロフィール初期化など複数の購読者が動作

**結果整合性（Eventual Consistency）:**
- 分散システムで即座の一貫性を保たず、最終的に一貫した状態に収束
- イベントスキーマを厳密に設計し、データ同期の正確性を確保
- リトライロジック、デッドレターキューでメッセージ喪失を防止

```python
# Pub/Sub実装例
event_bus.publish("user.registered", {
    "user_id": "12345",
    "email": "user@example.com",
    "timestamp": "2024-01-01T10:00:00Z"
})
```

## 2. マイクロサービスパターン

**マイクロサービスの特性:**
- 機能を独立したサービスに分割
- 各サービスが独立したデータベースを所有（Database per Service）
- API経由でサービス間連携

**サービス切り出しの判定:**
- ビジネスドメイン毎に分割（Domain-Driven Design）
- 開発チームの独立性を確保可能か
- 独立したスケーリングが必要か

**API設計と通信:**
- RESTful API またはgRPCで通信
- バージョニングにより、後方互換性を確保
- タイムアウト、リトライ、サーキットブレーカーで障害対応

---

## 3. 段階的移行パターン

**ストラングラーパターン:**
レガシーシステムの機能を段階的に新システムに置き換え、最終的にレガシーシステムを廃止します。

```
┌─ 既存システム ─────────────┐
│  ├─ 移行済み機能          │  (新システムへ)
│  └─ 移行待ち機能 ── API Gateway ── 新システム
└────────────────────────────┘
```

**フォールバック機構:**
- 新システムの障害時は、既存システムにフォールバック
- ファサード層（API Gateway）でルーティングを制御
- ユーザーへの影響を最小化

## 4. 技術的負債管理

**技術的負債の4象限:**
```
     高影響
  ┌─────────┐
  │ 優先度  │ 低優先度
低 │  高    ├─────────┐ 高
  │        │ なるべく│
  └─────────┤  避ける│
    低影響  └─────────┘
```

**負債の利子（Interest）:**
- 不安定なコードは、機能追加や修正に時間がかかる（金利）
- 利子を最小化するため、定期的な返済が必要

**返済戦略:**
- 高影響・高優先度：本スプリント内で解消
- 高影響・低優先度：計画的に解消を検討
- 低影響：許容するか、スプリント内の余時間で対応

負債の可視化（技術的負債ボード、テクノロジーレーダー）により、チーム全体で共通認識を形成します。

## 5. リリース・デプロイ戦略

**フィーチャートグル（Feature Flags）:**
- コードをマージしても、機能をオン/オフで制御
- 本番環境でも段階的に有効化可能
- ロールバックが即座に可能

```python
if feature_flags.is_enabled("new_checkout_flow", user_id):
    # 新しいチェックアウト処理
    return new_checkout()
else:
    # 既存のチェックアウト処理
    return legacy_checkout()
```

**ブルーグリーンデプロイメント / カナリアリリース:**
- **ブルーグリーン:** 2つの本番環境（青・緑）を切り替え。即座のロールバック可能
- **カナリア:** 新バージョンを一部ユーザーに先行配信。問題がなければ全体に展開

**無停止DBマイグレーション:**
- 古いカラムと新しいカラムを並行運用
- アプリは両方に書き込み、読み取りは新カラムから
- 段階的に依存を削除し、最終的に古いカラムを削除
